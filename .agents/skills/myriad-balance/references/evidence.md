# 一份报告怎样保留证据

复制 [review-template.json](../assets/review-template.json)，填写 `title`、`baseline`、`scenario` 及 `conditions`。`baseline` 标明被评价的游戏提交或快照摘要，原型、日志或策划记录另在对应行给出处。跨版本比较时分别保留两边规则和场景版本。

`observations` 的每行有 `metric`、`basis`、`value`、`unit`、`note`、`source`。数字 0 是有效读数，带单位的数把单位放在 `unit`。定性反馈用文字。工具采用以下依据名称。

| 依据 | 如何填写 |
| --- | --- |
| 源码核对、理论上界、离线推演 | 给源码版本／报告及范围。理论上界说明约束是否可同时满足，离线推演说明动作、配点与假设 |
| 引擎抽检 | 填同输入实跑的小项与来源，说明覆盖了单击、单次施放或完整序列中的哪一项 |
| 真人反馈、策划目标 | 区分观察到的表现与期望结果，链接原始记录，可保留定性原话 |
| 未测、缺输入、不适用 | `value` 填 `null`。在 `note` 解释缺哪个输入、待测什么或为何不适用 |

仅在需要出提醒时填整数 `level`。1 表示确定差异，2 表示经校准的参考范围或角色契约出现偏离，3 表示试测、趋势或覆盖缺口。标明出处及适用范围，复审时可以修订参考值。人工改值与游戏构建照常进行。

`checks` 记录技术执行，每行含 `name`、`status`、`source`。状态为“通过”“失败”“未运行”或“证据不足”，对已经运行的通过／失败项给出日志或 XML。把历史记录标在项目名或观察说明里。`reproduce` 按顺序列出检出前提、命令或复现场景。

`scripts/render_review.py` 从本地 JSON 生成 Markdown，可重定向保存。诊断与实际专项失败都原样展示。命令返回值只反映报告文件能否读取和解释。它不启动游戏或替代离线求解器。
