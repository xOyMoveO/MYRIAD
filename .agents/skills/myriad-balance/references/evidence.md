# 证据记录与报告格式

## 前后对照分层

移交数值改动或回答“改了什么”时，先用一段玩家能直接感知的摘要点出主要变化（例如清野生命、经验倍率、冷却、补给或购点规则），再将明细分为三层：

1. **正式实改**：当前生效数值或结算口径确实变化的项，列出改前、改后与影响场景。
2. **仅核对未变**：已复核但保留现值的角色或技能只报汇总计数（例如“其余 N 个技能仅核对、保留现值”），不与实改项混排。
3. **试改未采纳**：隔离实验或候选方案单独标注状态与结论。

跨 `formatVersion` 对比时，将“新增导出的既有字段”与“真实改数”分开说明。可用 `scripts/diff_snapshots.py` 生成初稿。

## 单议题评审卡（JSON → Markdown）

需要就单一平衡问题归档可复核读数时，复制 [review-template.json](../assets/review-template.json)，填写 `title`、`baseline`、`scenario`、`conditions`，可参照 [夜影实例](../assets/yingxiao-review.json)。`baseline` 标明被评价的源码提交、配对发行或快照摘要；跨版本比较时同时保留两边规则和场景版本。

从仓库根目录渲染随附实例（仅使用 Python 标准库，替换末尾路径即可渲染自定义报告）：

```sh
python .agents/skills/myriad-balance/scripts/render_review.py .agents/skills/myriad-balance/assets/yingxiao-review.json
```

`observations` 每行含 `metric`、`basis`、`value`、`unit`、`note`、`source`。数字 `0` 是有效读数，带单位的数将单位填在 `unit`，定性反馈用文字。依据名称约定如下：

| 依据 | 如何填写 |
| --- | --- |
| 源码核对、理论上界、离线推演 | 给源码版本／快照摘要及范围。理论上界说明放宽了哪些约束，离线推演说明动作、配点与假设 |
| 引擎抽检 | 填同输入实跑的小项、过滤器名与日志／XML 来源，说明覆盖单击、单次施放还是完整序列 |
| 真人反馈、策划目标 | 区分观察到的表现与期望结果，链接原始记录，可保留定性原话 |
| 未测、缺输入、不适用 | `value` 填 `null`，在 `note` 解释缺哪个输入、待测什么或为何不适用 |

## 非阻断提醒与技术执行

- **非阻断提醒**：仅在需要提醒时填整数 `level`：`1` 表示确定差异，`2` 表示偏离已校准参考范围或角色契约，`3` 表示试测输入、趋势或覆盖缺口。标明出处与适用范围；全部提醒仅供策划判断，人工设值照常保存、构建、试玩、合并与发布。
- **技术执行（`checks`）**：每行含 `name`、`status`、`source`。状态取 `通过`、`失败`、`未运行` 或 `证据不足`，已运行项必须附日志或 XML 来源，历史记录在名称或说明中标明版本。
- **复查步骤（`reproduce`）**：按顺序列出检出前提、命令与读取路径。`render_review.py` 返回值仅反映报告 JSON 格式是否合法，不启动游戏或替代离线求解器。
