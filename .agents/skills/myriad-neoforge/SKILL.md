# 万象（MYRIAD）NeoForge 开发规范

工程根目录为包含 `AGENTS.md`、`gradle.properties` 与 Gradle Wrapper 的当前检出目录；本文项目路径均相对该根目录。先读取 `AGENTS.md` 与 `docs/agents/domain.md`，再按其指引阅读 `docs/协作开发与内部命名.md` 及相关源码。Minecraft、NeoForge、Java 与模组版本以当前构建配置为准，不直接套用旧版接口。

## 名称与角色方向

- 对外中文名“万象”，英文名“MYRIAD”；原项目名仙凡劫。新增界面、介绍与文档使用新名称，历史记录和素材来源不追溯改写。
- 角色题材包罗万象，不默认限于修仙、仙侠或东方玄幻。可按核心机制与定位设计奇幻、科幻、现代、历史、神话、机械等角色；视觉、武器、命名与音效遵循各角色主题，不强制套用灵力/符咒或东方玄幻装饰。现有角色、技能名称和地图主题保持，除非用户另有要求。
- 当前模组ID、资源命名空间、NBT与测试属性前缀为 `myriad`，Java包为 `com.myriad`，入口为 `Myriad` / `MyriadClient`，命令为 `/myriad`。这是破坏兼容的身份迁移；先在新测试世界验证，旧存档迁移须独立确认和备份。
- 定位、兼容边界与协作约定见根目录 `AGENTS.md` 和 `docs/协作开发与内部命名.md`。原作者外部策划文件仅在实际可访问且与任务相关时读取。

## 先确认当前实现，而非沿用历史记录

- 开始任务先读相关源码与仓库内最新交接、验证记录；用 `rg --files docs` 定位相关文件。区分“用户确认的目标”“已写入源码”“已构建”“已安装”“实机验收”；任何一项不能代替其他项。
- 角色池、技能分支与成长系统以当前 `CharacterType`、`FirstGroupSkills`、`FirstGroupGrowth`、`LevelSystem` 为准。`FirstGroup` 是历史命名，不能据此推断仅有五个角色或其他角色仍走旧版系统。
- 符石系统已删除，不恢复抽取、符石库、属性或触发效果；只维护当前源码明确保留的清理边界。
- 基础生命、伤害、NPC、建筑与经济的接入范围须查实际调用链；专项机制测试不能证明实战平衡完成。
- 历史全局动作系统已移除，部分角色的第一人称手臂和武器有独立实现；修持刀或视觉表现时不恢复整套旧动作系统。按当前任务处理 motion 位移、伤害、冷却、粒子、音效和原版动作。
- 历史灵源运输、灵源核心、人界/仙界规则或旧技能数值可能仍有兼容代码，不将其视为新开发目标；只按当前任务和实际调用链处理。不要因更新规范就删除旧类、保存字段或资源。

## 架构与入口

- 服务端权威决定选择、资源消耗、冷却、目标、伤害和位移。客户端负责输入、显示、局部预测；所有请求经 `network/NetworkSetup` 重新校验，不能以客户端界面限制代替服务端限制。
- `PlayerData` 保存玩家持久状态；`PlayerDataProvider` 管理生命周期与同步；`GameManager` 管理阶段、队伍与对局；注册表保存定义。维护 `copyStateFrom`、序列化、重连和数据包兼容性，避免重复补发技能点或旧状态复活。
- 普通操作遵守 `GameManager.Phase`，正式玩法设置仅允许开局前由有权限者调整；训练模式按其显式开关放宽限制，不绕过角色/点数/目标校验。
- 队伍与选角规则以 `GameManager.onPick`、`PlayerDataProvider.chooseCharacter` 为准；双方共享角色池时不能从 `CharacterType` 的历史阵营字段重新制造职业阵营限制。保持选角轮次与重复角色约束。
- 玩家文本优先放进 `assets/myriad/lang/zh_cn.json` 与 `en_us.json`。描述应解释用途、命中条件、当前等级数值、蓝耗和当前CD，不只列技能名或过时公式。

源码入口索引见 `docs/协作开发与内部命名.md`，按任务定位 `src/main/java/com/myriad/` 下当前实际文件，不照搬历史角色或已删除系统的类名。

## 分组重做，但按角色、按技能写代码

- 角色分组与批次名称不是运行时的技能实现单位。每个角色单独目录，每个被动、主动和分支单独文件；让某个技能可以被另一个角色单独复用。
- 具体公式、触发条件、控制、持续效果、表现与二段逻辑归具体技能类。角色绑定文件登记候选、角色成长和资源关系；批次注册器只处理登记、解析与分支校验。不要在共享运行时按角色ID/技能ID堆叠玩法大switch。
- 共用层只提供选点、扫掠弹体、motion、护盾、任务、命中事件和绘制原语。复用时注入独立定义/ID，检查状态来源、动作/图标绑定与目标过滤，不搬走原角色的整套技能。
- 每角色8个候选：被动A/B各上限5、二选一；常规一/二各上限5、均可学；主要A/B各上限7、二选一；终极A/B各上限3、二选一。实际为1被动+4主动，已选五项点满需25点，但角色20级最多20技能点（含开局点）。
- 第一次投入点数锁定对应分支，服务端同时校验角色归属、互斥、等级门槛、单技能上限和总预算。不要把旧“小技能不超过其他两个之和”规则直接套到新图谱。终极目前沿用4/8/12级门槛，只是首版节奏，不自动视为最终设计。
- 新版HUD、CD同步、加点和介绍使用已选分支解析，不固定读取旧 `CharacterType.skill(slot)`。升级不自动回满生命/法力；训练切角色返还技能点，但不凭空退款或重发五属性购买次数。

## 构筑与数值

- 新版力量仅增强基础普攻A；智慧增强技能强度S，包括物理技能、被动附加、治疗与护盾。强化普攻的基础部分与技能附加部分分开结算；不能让力量同时放大技能。控制时间、范围、距离、冷却等不自动乘智慧。
- 新版金币加点为力量、智慧、速度、防御、冷却：每局合计最多15次，单项最多10次；每点花费金币。收益/价格读 `FirstGroupGrowth` 的当前实现，不把首版测试值固化成永久规范。
- 基础生命按角色升级成长，五属性不加生命，符石已移除且不再提供生命。具体预算与已接入范围以当前角色定义和验证记录为准，不把历史测试值固化为永久规范。
- 新版暴击固定1.5倍，保留暴击率，不从旧暴击伤害属性获得额外倍率。法力限制连续释放；检查技能循环与技能返蓝，避免多段重复返蓝或无损耗无限施法。
- 常规装备、补给与属性入口先核对当前调用链；不要因为历史实现曾存在，就恢复已停用的装备收益。
- 符石系统删除后，不擅自把原符石收益迁到五属性或角色技能，也不清零既有基础生命/法力；新的穿透、吸血、韧性等构筑渠道需用户确认。旧存档忽略已删除字段，清理 `rune_` 修饰符/buff/护盾及旧控制标签；不得清除角色护盾、技能状态或名字带rune的野怪奖励。
- 保留物理/魔法/真实区分，走统一减伤、护盾和有效伤害事件。公式写入角色/技能/属性本身，不重新加全局隐含倍率；持续/派生伤害不能循环触发自身或二次暴击。护盾全部使用模组护盾，按来源隔离，同源续盾按技能规则处理，不用原版吸收生命冒充。

## 选点、位移与特效

- 非瞬移位移必须由服务端计算方向、逐tick速度、身体扫掠碰撞、时间/距离、落点和停止条件，并同步对应客户端；不能用 `teleportTo` 或直接写位置替代。真正闪烁、交换、回城和阵点传送可用经过验证的瞬移。
- 从 `AbilityRuntime`、当前网络载荷与 `DashController` 追踪实际位移链路再修改；不要套用已退役角色的旧实现。首步也校验，不能只测终点；末步受终点约束，碰撞/控制与自然结束分别处理，精确选点停稳，普通突进可保留受控少量惯性。
- 跃进预检全弧线净空与合法落点，不在计时结束但尚未落地时结算落地伤害。处理区块/边界、天花板、动态障碍、打断和有限等待；死亡、换角、退出、关闭模组、重置必须释放服务端速度和客户端控制，不能留下旧任务。
- 地面范围技能与玩家站立位置分开校验，使用 `requiresStandingPoint` 和 `AbilityTargeting`。预览与确认共用范围/支撑/净空/路径规则；落点和释放半径仅本人可见。失败或取消选点不扣蓝、不进入CD；实际施法后才提交费用与冷却。不得借投影越过范围或墙体。
- 多充能必须逐层顺序恢复：一次CD回复一次，直至充满，不把各层当独立并行CD。在技能图标下显示次数，数字外围用连续填充圆环表示下一层剩余/总CD；0层要明确同步，充能计数不作为右上角普通buff显示。
- 二段释放分别绑定表现/图标与可释放窗口，图标上方显示剩余时间；二段不重复缴纳已包含费用。复用旧图标加标记只能标为过渡实现，不能宣称专属两套图标已制作。
- 每技能在自己的表现入口组织预警、轨迹、命中、持续和结束。程序化几何可共用，但避免所有技能套同一团粒子；限制数量、频率和寿命，不遮挡施放者视线。攻击型技能排除友军与建筑，辅助增益/治疗作用于合法友军；技能伤害/控制不作用于防御塔等建筑，普攻拆塔走专用攻击链。
- 音效优先符合兵器/材质/角色的拟真反馈，不能把刺耳电子音作为默认风格。有音频接入任务时用 `myriad-audio`；有技能图标生成任务时用 `myriad-skill-icons`。不因增加特效或研究Blender就恢复历史全局动作系统。

## 技能特效制作

制作、修改或验收技能特效（含飞行物、拖尾、命中、范围和持续效果）时，先读 [多层高清 2D 与模型主体规范](references/layered-vfx.md)，再拆分各技能的表现。该文档统一规定高清 2D 分层、飞行物模型主体、2D 像素修饰与视觉验收要求。

## 地图、模式与原版恢复

- 5v5与3v3共处同一存档，模式设施路由经 `MatchArena`；共享大厅不混入战场配置。地图边界、兵线、草丛、野怪、塔/水晶等相关设施按现有存档配置保存，不迁回机器全局路径。地图操作遵守管理员和对局阶段校验。
- 3v3当前为单线布局，公平性关注路线、通行净空、阵地和营地位置对称；建筑外观可以不同。没有用户要求，不因修改代码就自动重建或覆盖地图。
- 模组关闭应恢复原版界面、属性、队伍名称与旁观行为；跟踪恢复逻辑，不把模组默认规则泄漏到原版。复活、回城、训练与重连也需正确清理临时状态。

## 验证、记录与交付

1. 追踪状态→服务端校验→效果→同步→客户端显示；持久状态另测保存、克隆/重连和清理。
2. 修改代码通常在项目根执行 `bash ./gradlew build`（Windows 使用 `.\gradlew.bat build`）；角色技能相关优先跑隔离的 `runFirstGroupTestServer`，选点/motion覆盖当前空间验证入口。资源新增补齐模型/贴图/语言/声音定义和注册。只改技能说明或策划无需构建游戏。
3. Java 工具链和 Gradle 缓存须检查当前环境；仅在依赖已缓存时使用 `--offline`。不依赖作者机器上的外部 init 脚本，也不擅自改变工程工具链。
4. 专项通过不等于全量通过、客户端画面、延迟手感或实战平衡验收。地图专项可能需要外部世界 fixture；以当前配置和可用材料为准，只报告实际跑过的结果，不为了绿灯关闭无关断言。
5. 网络新增/变更需处理协议和双端一致性，协议版本以源码为准。分别核对 JAR 内容、构建时间和安装状态。部署遵守根目录 `AGENTS.md` 的当前授权与身份迁移安全例外；从已确认配置获取实例与备份目录，检查运行状态、备份及 SHA256，不停止用户游戏。
6. 已完成的玩法、平衡、UI、音效、视觉或内容更新，按根目录 `AGENTS.md` 及仓库既有日志约定追加当天玩家可读条目，保留历史；外部日志不可访问时如实报告待同步。写清玩家能感知的变化与未验收范围，不用内部类名代替更新说明。
7. 系统或角色状态有实质变化时同步仓库相关交接和状态文档；外部状态文档按已确认位置访问，不可访问时报告待同步。策划与实现分开标注，原始策划未经要求不覆盖。仅规范维护写开发记录，不假称发生游戏更新。
